# PyTorch 2.13 NPU 环境准备

## 首次使用必须告知用户的配置

开始远程准备前，先用简短说明告知用户：复制 `assets/connection.example.json` 到自己的私有目录，每台主机只填写 `ip`、`username`、`password`，多台按优先级添加到 `hosts`；填好后只提供文件路径，不在聊天中提供密码。容器、Python/CANN 路径及空闲卡自动检查，不要求用户手填。已提供的连接文件直接复用，不重复索要。

默认目标为本技能的 PyTorch 2.13 和指定官方主干源码，无需用户再配置源码路径。只有自动检查发现无法解决的环境缺口时，再说明缺少什么并询问必要信息。

准备可追溯、不会误用基础镜像框架的独立运行环境。仅处理容器、依赖、源码构建和小型设备/编译验证；环境就绪不等于模型 benchmark 通过。benchmark 数据收集使用对应 skill，另按用户要求审核命令。

## 首次配置与边界

先读 [配置与连接](references/configuration.md)，确认执行位置、镜像、容器、工作目录、Python、CANN 与输出位置。无需 Windows、WSL、固定 PC 路径或其他未附带技能。

需要自动连接或多主机选卡时，读 [连接池与凭据文件](references/remote-pool.md)。模板为 `assets/connection.example.json`，由用户在私有目录填写后提供文件路径，凭据不回显；当前主机无可用卡时检查授权名单中的下一台容器环境，不使用未授权主机。

新容器命名与归属遵循连接池文档：使用当前使用者标识、目标版本和唯一任务标识，不继承原作者的姓名缩写。自动复用必须核实当前使用者和任务标签，不能仅因版本匹配就使用他人容器。

- 用户指定 torch_npu 源码仓库为 `https://gitcode.com/Ascend/pytorch`，要求使用最新主干自动根据实际 PyTorch 版本构建。不能擅自替换成预编译 torch_npu 包或旧版本分支。
- “main”若指主干概念，先用远端 HEAD 核实实际分支；本项目实测为 `master`，不存在 `main`。如用户明确指定字面分支且不存在，应说明差异，不静默替换。
- 按当前用户授权进行容器创建、环境下载安装和设备验证；历史项目授权不对新用户生效。特权模式须有当前环境授权；不停止其他人的任务，不顺便改宿主机驱动或启动 benchmark。
- 新版本使用新容器、工作目录和独立依赖环境，保留已完成的2.14环境及产物。不要只改容器名、镜像标签或版本文件来制造“2.13”。
- 远程执行与凭据处理按上述配置文档操作；不内置主机、账户或凭据位置。

## 准备顺序

1. 从用户当前环境发现资产，核实镜像不可变 ID、架构、驱动挂载和工作目录。[已验证实例](references/verified-instance.md) 是可选技术案例，不提供默认主机、镜像或必需的外部脚本。
2. 查实际 `torch.__version__`、`torch.__file__` 及对应解释器。曾出现 `npu-v2130` 容器实际是2.14，禁止仅凭名称判断版本。
3. 创建不固定卡号的独立容器，保留CANN和只读驱动挂载。如果需要特权模式，先核实当前授权；卡环境变量不构成安全隔离。不要因暂时无空闲卡而反复重建容器。
4. 按 [安装与构建流程](references/build-and-verify.md) 创建不继承系统site-packages的venv，安装官方PyTorch2.13 CPU wheel，实际导入检查通过后再构建插件。CPU wheel可配合torch_npu执行NPU，不代表任务只用CPU。
5. 查询官方仓库最新主干并固定本次HEAD，初始化固定版本子模块，按当前源码说明准备构建工具。检查requirements中的框架版本约束，避免它把2.13升级为nightly2.15/其他版本。
6. 清除残留TORCH_VERSION/PYTHONPATH，使用实际venv解释器和官方 `ci/build.sh --python=<版本>`，让源码检测已安装的PyTorch。不要手改版本号。保留构建命令、commit、子模块版本、日志、退出码及wheel SHA256。
7. 为交互/登录shell配置明确的2.13激活入口；非shell docker exec显式使用venv解释器。检查旧npu-mode/npu-run-suite是否硬编码基础镜像路径，不把它们默认当作2.13入口。
8. 在任务启动前自动选择空闲NPU、复查并取得项目协作锁，设置可见设备后才导入/初始化NPU，单轮固定一卡。没有空闲卡则报告；不终止其他任务或擅自共享运行。协作锁不能约束其他使用方。
9. 验证版本/路径、依赖、NPU加法、eager反向及DVM编译前后向结果/梯度。仅安装成功、仅import成功都不足以声称图模式就绪。缺依赖可在授权范围补齐并复查；若需修改上游框架/插件源码，不将其伪装为普通环境修复，先说明原因及范围。
10. 回收版本和构建证据、失败与成功验证报告，校验文件清单，交付容器名、进入方式、激活入口、已通过项和未完成项。每分钟内更新长构建的实际进展，完成后及时报告。

## 验收与解释

- 2.13正式版、2.13开发版和2.14开发版分别记录，不把它们当成等价框架。
- Triton必须分别记录import版本、triton distribution和triton-ascend distribution。本项目实际出现3.5.0/3.6.0/3.6.0+git0cfb1708差异；不要修改版本字符串来消除差异。
- 同一基础镜像保留其他版本本身不代表污染；隔离venv、正确的默认shell和实际导入路径是关键。非shell入口仍可能绕过shell激活，交付时必须说明。
- 最新torch_npu主干与旧版本数据的软件栈不同，跨版本性能变化不能全部归因于PyTorch版本。不要为追求“单变量”擅自重建原有已完成环境。
- 重复出现相同确定性构建/兼容错误时，停止盲目重试，保留证据并说明具体阻塞；不要未经授权替换目标版本、关闭关键后端或改源码以宣称通过。
