# NPU技能：三类职责，环境按版本独立维护

| 技能目录 | 职责 |
| --- | --- |
| `npu-remote-container` | 负责SSH密钥登录、自动连接宿主机、创建/连接本人任务容器、空闲卡选择、多主机回退及文件传输 |
| `pytorch213-npu-environment` | 负责 PyTorch 2.13 + torch_npu + CANN 9.2.0 正式版环境的创建和准备；该组合已经过 NPU 运算、图模式前后向、profiler 及备份试恢复验证 |
| `pytorch214-npu-environment` | 负责 PyTorch 2.14 + torch_npu + CANN 9.2.0 正式版环境的创建和准备；该组合已经过 NPU 运算、图模式前后向、profiler 及备份试恢复验证 |
| `npu-graph-benchmark-collect` | 负责融合范围、融合效果、无调试基线的运行、完整产物回收、核验、采集记录及 NPU 耗时/加速比表格 |

上述四个技能目录分别放入自己的 `$CODEX_HOME/skills/`，未设置时使用当前用户主目录的 `.codex/skills/`。保留目录内相对结构，无需与作者的PC/WSL路径一致。默认分享包包含三类能力、四个独立技能。2.13、2.14环境技能分别维护，未来2.15也新增独立环境技能，不合并成通用版本选择器。2.15尚未建立或验证，不承诺已有支持。

“已经过验证”指2026-10-23记录的软件栈与硬件实例；新用户的宿主机和新构建仍需实际验证。环境技能负责软件方案与准备，涉及SSH和Docker创建时调用远程容器技能执行，两个版本仍独立维护。

## 环境准备的依赖与镜像来源

这不是裸机装机技能。宿主机需已有可用NPU、兼容驱动、Docker及操作权限；远程执行还需SSH连接，下载源码/软件包时需网络或离线安装材料。创建容器需要可获取的基础镜像，源码构建还需足够CPU、内存和磁盘，以及Git、编译器、CMake、Ninja、Python开发工具、torch_npu子模块和依赖。模型软件包与数据按所选benchmark另行准备。

可以创建全新容器，也可以验证后复用本任务的独立容器；不会重装已就绪环境，也不会自动借用其他人的容器。新容器始终从镜像启动，不是从空白文件系统开始安装宿主机驱动。

本次CANN来源是官方公开镜像：

```text
swr.cn-south-1.myhuaweicloud.com/ascendhub/cann:9.2.0-910b-ubuntu22.04-py3.12-devel
```

该镜像用于本次Ascend910B/ARM64实例，不能据此声称包含所需PyTorch和torch_npu。本次2.14是在原有已验证框架镜像基础上组合官方CANN9.2.0组件；2.13另复制本项目已构建的独立venv。原框架基础镜像没有已确认的公开下载地址，不将其本地ID写成他人可以直接拉取的仓库名。

其他使用者可选择：已有本人可访问的匹配镜像；或官方CANN开发镜像，加上可获取的目标PyTorch构建和按版本源码构建的torch_npu。目标PyTorch构建不可获取时需补齐其源码构建条件并固定ref，不能换成别的版本冒充。技能包只含工作流和必要工具，不包含大型容器镜像、wheel或凭据。具体已验证版本、来源和依赖缺口见两个环境技能各自的`references/verified-instance.md`。

## 用户只需填写的连接配置

仅需要远程连接时，复制 `npu-remote-container/assets/connection.example.json` 到自己的私有目录：

```json
{
  "hosts": [
    {"ip": "主机IP", "username": "用户名"}
  ]
}
```

默认使用SSH密钥登录，配置不保存服务器密码。复用实际控制端已有的SSH密钥、ssh-agent和SSH配置，自定义密钥才选填`identity_file`本机路径。私钥始终保留在本机，只有公钥安装到服务器；建议给私钥设置口令并由本机agent解锁，后续自动执行无需输入服务器密码。首次配置通常需用户交互登录一次或由管理员追加公钥，具体流程见远程技能的`references/remote-pool.md`。修改技能本身不会自动改变现有服务器认证。

填写后只提供配置路径，不把真实主机名单、私钥或口令放入聊天、仓库、容器及分享包。多台按顺序添加。容器名、环境路径、卡号自动发现/生成；当前主机无空闲卡时检查下一台，但不借用他人的容器。各技能不重复要求填写这份配置，连接模板只由远程技能维护。Windows和WSL使用各自的SSH客户端与密钥/agent，执行时明确控制端；重装后的服务器主机密钥要重新核实。

## 可以分三次请求

1. “使用 $npu-remote-container 连接我提供的主机，准备本任务独立容器，暂不安装框架。” 如需新容器而尚未确定镜像，它会先明确镜像需求；不能凭空创建执行环境。
2. “使用 $pytorch214-npu-environment 在这个任务容器准备 PyTorch2.14 + torch_npu + CANN9.2.0正式版，只安装并验证，不跑模型。” 如果先指定了现成环境，可直接检查复用，不能为形式统一重装。
   准备2.13时明确调用 `$pytorch213-npu-environment`，不把2.14技能当作通用版本入口。
3. “使用 $npu-graph-benchmark-collect 在已验证环境收集 DCGAN 训练的融合范围、融合效果和性能基线，先提交方案和命令审核。”

也可以一次授权完整流程，执行代理按这三类职责依次工作，但不因为调用了其中一个就扩大任务范围。benchmark命令仍按约定审核。已有连接/容器、已准备环境直接复用上下文，无需重复运行前两步；离线汇总已有日志可以只使用采集技能。

## 阶段之间交接什么

- 远程技能输出不含凭据的 `execution_context.json`：主机/容器、归属、镜像、工作目录、设备映射与锁范围。
- 环境技能输出 `environment_report.json`：实际PyTorch/torch_npu/CANN版本、解释器、激活路径、来源、验证结果和依赖缺口。原始连接文件不进入报告。
- 采集技能只读复核上述信息，缺环境或模型依赖时返回缺口；只有用户授权环境准备时才转交安装，不在采集技能内部偷偷安装。

## 三类采集

| 阶段 | Debug | Profiler | 回收要求 |
| --- | --- | --- | --- |
| 融合范围 | 开 | 关 | 完整debug目录；核验前后向FX、output_code、ir_pre_fusion与ir_post_fusion |
| 融合效果 | 开 | 开 | 同轮完整debug和profiler原始/解析目录、数据库、时间线 |
| 正式性能基线 | 关 | 关 | 单步耗时、精度、版本与命令证据、加速比表 |

编译缓存默认留远端；分析产物回收后核验SHA256。历史CANN9.1.0数据不改标成9.2.0。debug/profiler轮耗时只作观测，正式加速比使用双关基线，不自动运行GPU或实施优化。

2.13和2.14安装步骤、依赖约束、来源和验证记录独立保留；可以采用一致的文档结构，但不能把版本号替换视为已完成新版本适配。

这些技能是供执行代理使用的工作流与必要工具，不是安装后自动常驻运行的调度服务。耗时汇总脚本只依赖Python3标准库；安装环境仍需要实际NPU驱动、CANN、对应源码与构建工具。

当前采集技能不包含GPU对比、性能原因分析、融合映射和最小复现；后续GPU数据到齐后，再单独建立分析流程或技能。
